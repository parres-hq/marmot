# MIP-06

## Multi-Device Support

`draft` `optional`

This document defines how users can operate Marmot on multiple devices simultaneously. Each device is an independent MLS leaf node that joins existing groups via External Commits, authorized through an out-of-band device pairing flow. This specification covers the authorization model, pairing protocol, payload format, and client recommendations for multi-device scenarios.

## Overview

Marmot's identity model naturally supports multiple devices. Each device generates its own MLS signing key and encryption key, but all devices belonging to the same user share the same Nostr public key in their MLS `BasicCredential` identity field (see [MIP-00](00.md)). This means a user with two devices in a group will occupy two separate leaf nodes in the ratchet tree, but both leaf nodes carry the same credential identity.

The multi-device model has these properties:

- **Independent state**: Each device maintains its own MLS group state, key material, and message history. There is no shared MLS state between devices.
- **Same logical identity**: All devices share the same Nostr pubkey, allowing clients to recognize multiple leaf nodes as belonging to one user.
- **Independent decryption**: Each device independently receives and decrypts group messages. A message sent from one device will appear on the user's other devices as a group message.
- **Forward secrecy boundary**: A new device cannot decrypt messages from epochs before it joined. This is a fundamental MLS property and is by design.

History synchronization between devices is out of scope for this MIP and is deferred to a future specification.

## External Commit Authorization

Devices join existing groups via MLS External Commits ([RFC 9420 Section 12.4.3.2](https://www.rfc-editor.org/rfc/rfc9420.html#section-12.4.3.2)). An External Commit allows a new party to add themselves to a group using a `GroupInfo` object, without requiring an existing member to come online and issue an Add proposal.

### Authorization Carve-Out

[MIP-03](03.md) requires that non-self-update Commits be sent by a member listed in `admin_pubkeys`. External Commits from new devices require a carve-out from this rule:

**An External Commit MUST be accepted when ALL of the following conditions are met:**

1. The credential identity (Nostr pubkey) in the joining LeafNode matches the credential identity of at least one existing group member
2. The External Commit includes a valid Resumption PSK proposal (see [Resumption PSK Requirement](#resumption-psk-requirement))
3. The External Commit includes a valid Nostr identity proof in `FramedContent.authenticated_data` (see [Nostr Identity Proof](#nostr-identity-proof))
4. The External Commit satisfies all standard MLS validation rules ([RFC 9420 Section 12.4.2](https://www.rfc-editor.org/rfc/rfc9420.html#section-12.4.2))

**An External Commit MUST be rejected when:**

- The credential identity does not match any existing member's credential identity
- The Resumption PSK proposal is missing or invalid
- The Nostr identity proof is missing or fails verification
- Any standard MLS validation check fails

This carve-out ensures that only the holder of a Nostr private key that is already represented in the group can add a new device. It does not allow arbitrary external parties to join.

### Validation Steps

When processing an External Commit, existing members MUST perform these checks in order:

1. Decrypt the outer NIP-44 layer using the current epoch's `exporter_secret` (standard `kind: 445` processing per [MIP-03](03.md))
2. Verify the MLS `PublicMessage` structure and signature per [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html)
3. Verify the credential identity in the joining LeafNode matches an existing member's credential identity
4. Verify the `authenticated_data` contains a valid Nostr identity proof (see [Nostr Identity Proof](#nostr-identity-proof))
5. Verify the Resumption PSK proposal references a valid epoch and the `confirmation_tag` matches (see [Resumption PSK Requirement](#resumption-psk-requirement))
6. Validate the LeafNode per [RFC 9420 Section 7.3](https://www.rfc-editor.org/rfc/rfc9420.html#section-7.3)

If any check fails, the External Commit MUST be rejected.

## Nostr Identity Proof

The Nostr identity proof binds an External Commit to the Nostr private key of the joining user. It is placed in the `FramedContent.authenticated_data` field, which is an application-defined opaque byte string that is covered by the MLS signature ([RFC 9420 Section 6](https://www.rfc-editor.org/rfc/rfc9420.html#section-6)).

### Why `authenticated_data`

MLS External Commits are self-signed -- the joining device signs with its own MLS signing key, which is distinct from the Nostr identity key. Without an additional proof, there is no cryptographic link between the External Commit and the Nostr identity claimed in the credential. The `authenticated_data` field solves this:

- It is explicitly application-defined: "It is up to the application to decide what authenticated_data to provide" ([RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html))
- It is covered by the MLS signature, binding it cryptographically to the External Commit
- It requires no extension negotiation or group-wide capability advertisement
- It does not affect MLS processing for non-multi-device scenarios (the field can be empty for normal Commits)

### Proof Construction

The joining device constructs the Nostr identity proof as follows:

1. Serialize the LeafNode from the External Commit's UpdatePath using TLS serialization
2. Serialize the target GroupContext using TLS serialization
3. Compute the challenge: `challenge = SHA-256("marmot-external-commit-v0" || serialized_LeafNode || serialized_GroupContext)`
4. Sign the challenge with the Nostr private key: `proof = SchnorrSign(nostr_privkey, challenge)`

The `authenticated_data` field MUST contain the following TLS-serialized structure:

```tls
struct {
    opaque domain_separator<V>;    // "marmot-external-commit-v0"
    opaque schnorr_signature[64];  // Nostr Schnorr signature over the challenge
} NostrIdentityProof;
```

### Proof Verification

Existing members verify the proof by:

1. Extract the `NostrIdentityProof` from `FramedContent.authenticated_data`
2. Verify the `domain_separator` is `"marmot-external-commit-v0"`
3. Serialize the LeafNode from the External Commit's UpdatePath
4. Serialize the current GroupContext
5. Compute `challenge = SHA-256("marmot-external-commit-v0" || serialized_LeafNode || serialized_GroupContext)`
6. Verify the Schnorr signature against the Nostr pubkey in the LeafNode's credential identity

### Security Properties

- **Identity binding**: Proves the Nostr private key holder authorized this specific LeafNode to join this specific group at this specific epoch
- **Replay prevention**: The GroupContext includes the epoch number and tree hash, preventing replay across epochs or groups
- **Domain separation**: The `"marmot-external-commit-v0"` prefix prevents cross-protocol signature reuse
- **Non-interference**: For non-External-Commit messages, `authenticated_data` MAY be empty; existing MLS processing is unaffected

## Resumption PSK Requirement

External Commits for multi-device joins MUST include exactly one `PreSharedKey` proposal with a Resumption PSK. This provides defense-in-depth: even if an attacker obtains a valid GroupInfo and forges an identity proof, they cannot produce a valid External Commit without the correct PSK value.

### PSK Configuration

The `PreSharedKey` proposal MUST use the following configuration:

- **`psktype`**: `resumption` (value `2`)
- **`usage`**: `application` (value `1`)
- **`psk_group_id`**: The MLS group ID of the target group
- **`psk_epoch`**: The epoch from which the `resumption_psk` was extracted
- **`psk_nonce`**: A fresh cryptographically random value of length `KDF.Nh` (32 bytes for ciphersuite `0x0001`)

### How It Works

The `resumption_psk` is derived from the MLS key schedule ([RFC 9420 Section 8](https://www.rfc-editor.org/rfc/rfc9420.html#section-8)) and is available to all current group members. The existing device provides the `resumption_psk` value to the new device during pairing (see [Device Pairing Flow](#device-pairing-flow)).

When existing members process the External Commit:

1. They look up the `resumption_psk` for the referenced group and epoch from their key schedule
2. They derive `psk_secret` per [RFC 9420 Section 8.4](https://www.rfc-editor.org/rfc/rfc9420.html#section-8.4)
3. The `psk_secret` is incorporated into the new epoch's key schedule
4. The `confirmation_tag` in the External Commit will only match if both sides used the same PSK value

If the PSK value is incorrect, the `confirmation_tag` verification fails and the External Commit is rejected. No explicit PSK verification step is needed beyond the standard MLS Commit processing.

### Why Resumption PSK

Resumption PSKs are preferred over External PSKs because:

- All existing members already possess the `resumption_psk` from their key schedule -- no pre-distribution is needed
- The PSK is identified by group ID and epoch, so existing members can look it up without additional coordination
- It proves that the new device received secrets from someone who was in the group during the referenced epoch

## Device Pairing Flow

Device pairing is a two-phase out-of-band exchange between an existing device (already a member of one or more groups) and a new device (not yet in any groups).

### Phase 1: New Device Presents Ephemeral Public Key

1. New device generates a fresh X25519 keypair (`ephemeral_privkey`, `ephemeral_pubkey`)
2. New device presents the `ephemeral_pubkey` (32 bytes) to the existing device

This presentation MAY use any suitable channel: a QR code (the 32-byte key fits easily in a single QR), NFC tap, Bluetooth advertisement, or manual entry.

### Phase 2: Existing Device Sends Encrypted Pairing Payload

1. Existing device prompts the user to select which groups the new device should join (all groups, or a subset)
2. For each selected group, the existing device extracts:
   - The `GroupInfo` object (with `external_pub` and `ratchet_tree` extensions)
   - The current epoch's `exporter_secret`
   - The `resumption_psk` for the current epoch
   - The `nostr_group_id` from the Marmot Group Data Extension
3. Existing device assembles a `PairingPayload` (see [Pairing Payload Specification](#pairing-payload-specification))
4. Existing device encrypts the payload using X25519 + ChaCha20-Poly1305:
   - Perform X25519 key agreement: `shared_secret = X25519(existing_ephemeral_privkey, new_device_ephemeral_pubkey)`
   - Derive encryption key: `key = HKDF-Expand(HKDF-Extract(salt=None, IKM=shared_secret), "marmot-pairing-v1", 32)`
   - Generate random 12-byte nonce
   - Encrypt: `ciphertext = ChaCha20-Poly1305.encrypt(key, nonce, plaintext_payload)`
   - The encrypted pairing message is: `existing_ephemeral_pubkey || nonce || ciphertext`
5. Existing device transfers the encrypted pairing message to the new device

The encrypted pairing message MUST be transferred via a channel with sufficient bandwidth for the payload size (see [Transfer Channel Considerations](#transfer-channel-considerations)).

### Phase 3: New Device Processes Pairing Payload

1. New device receives the encrypted pairing message
2. New device performs X25519 key agreement using its ephemeral private key and the existing device's ephemeral public key from the message
3. New device derives the encryption key using the same HKDF parameters
4. New device decrypts the payload
5. For each group in the payload, the new device:
   a. Generates a fresh MLS signing key and creates a credential with its Nostr pubkey
   b. Constructs an External Commit using the GroupInfo
   c. Includes the Resumption PSK proposal
   d. Includes the Nostr identity proof in `authenticated_data`
   e. Wraps the External Commit in a `kind: 445` event (see [Publishing External Commits](#publishing-external-commits))
   f. Publishes the event to the group's relays
6. New device securely deletes the ephemeral private key and all pairing secrets

### Retry Handling

The GroupInfo and `exporter_secret` are epoch-specific. If the group advances between pairing and External Commit publication, the attempt will fail. When this occurs:

- The new device SHOULD notify the user of the failure
- The existing device SHOULD re-extract the GroupInfo for the new epoch
- The pairing flow for the affected group(s) SHOULD be retried
- Groups that were successfully joined do not need to be retried

## Pairing Payload Specification

The pairing payload is a TLS-serialized structure containing all data the new device needs to issue External Commits.

### TLS Structure

```tls
struct {
    opaque exporter_secret[32];      // Current epoch's exporter_secret
    opaque resumption_psk[32];       // Current epoch's resumption_psk
    opaque psk_group_id<V>;          // MLS group ID (for PSK identification)
    uint64 psk_epoch;                // Epoch number (for PSK identification)
    opaque nostr_group_id[32];       // From Marmot Group Data Extension
    opaque group_info<V>;            // TLS-serialized GroupInfo with external_pub
                                     // and ratchet_tree extensions
} GroupPairingData;

struct {
    uint16 version;                  // Payload format version (current: 1)
    GroupPairingData groups<V>;      // Vector of per-group pairing data
} PairingPayload;
```

### Field Details

- **`version`**: Payload format version number. Current version is `1`. Version `0` is reserved and MUST be rejected. Future versions MAY append additional fields to `GroupPairingData`.
- **`exporter_secret`**: The 32-byte MLS exporter secret for the current epoch, used by the new device to encrypt the outer NIP-44 layer of the `kind: 445` event containing the External Commit.
- **`resumption_psk`**: The 32-byte resumption PSK for the current epoch, included by the new device in the External Commit's `PreSharedKey` proposal.
- **`psk_group_id`**: The MLS group ID, used in the `PreSharedKeyID` to identify which PSK to use. This is the private MLS group ID, NOT the `nostr_group_id`.
- **`psk_epoch`**: The epoch number from which the `resumption_psk` was derived.
- **`nostr_group_id`**: The public group identifier from the Marmot Group Data Extension, used for the `h` tag in the `kind: 445` event.
- **`group_info`**: The TLS-serialized `GroupInfo` object for the current epoch. MUST include the `external_pub` extension (required for External Commits) and the `ratchet_tree` extension (required for the new device to compute the UpdatePath).

### Version Handling

- **Version `0`**: Reserved and MUST be rejected
- **Version `1`** (current): Format as defined above
- **Future versions**: Higher version numbers indicate newer formats. Implementations SHOULD attempt forward compatibility by parsing known fields and ignoring unknown trailing fields in `GroupPairingData`.

### Confidentiality Requirements

The pairing payload contains highly sensitive data including group secrets, PSK values, and group metadata. The payload MUST be encrypted before transfer regardless of the transfer channel used. The encryption scheme is specified in [Phase 2](#phase-2-existing-device-sends-encrypted-pairing-payload) of the pairing flow.

## Pairing Payload Size Estimates

The following table provides approximate payload sizes to help implementors choose appropriate transfer channels. Sizes are for the raw TLS-serialized `PairingPayload` before encryption.

Per-group size is approximately `570 + 288 * N` bytes, where `N` is the number of members in the group. This accounts for the GroupInfo (including GroupContext, `ratchet_tree`, and `external_pub` extensions) plus the per-group secrets overhead (~108 bytes).

### Size Reference Table

| Scenario | Groups | Avg members | Per-group size | Total payload | With compression (~30%) |
|---|---|---|---|---|---|
| Minimal | 1 | 5 | ~2 KB | **~2 KB** | ~1.4 KB |
| Light user | 5 | 10 | ~3.4 KB | **~17 KB** | ~12 KB |
| Typical user | 10 | 20 | ~6.3 KB | **~63 KB** | ~44 KB |
| Power user | 30 | 30 | ~9.2 KB | **~276 KB** | ~193 KB |
| Heavy user | 50 | 50 | ~14.9 KB | **~745 KB** | ~522 KB |

> **Note**: Compression ratios are estimates based on Zlib with typical MLS data. Actual ratios depend on group metadata (names, descriptions, relay URLs) and tree structure. The ratchet tree dominates payload size for larger groups.

### What Drives Size

- **Ratchet tree**: ~288 bytes per member (LeafNode ~219 bytes + ParentNode ~69 bytes). This is the dominant factor.
- **GroupContext**: ~321 bytes per group (fixed fields + `marmot_group_data` extension)
- **GroupInfo overhead**: ~103 bytes per group (confirmation tag, signer, signature)
- **Pairing secrets**: ~108 bytes per group (exporter secret, resumption PSK, PSK identifiers, nostr_group_id)

## Transfer Channel Considerations

The pairing payload format is channel-agnostic. Implementations choose their own transfer mechanism based on the user's needs and the payload size. The specification defines only the payload format and encryption; the transfer channel is an application-level concern.

### Channel Suitability

| Channel | Practical capacity | Characteristics |
|---|---|---|
| Single QR code | ~2 KB | Simple, suitable for 1 small group only |
| [BBQr](https://bbqr.org/) (animated QR) | Up to ~250 KB | Air-gapped, no network required, widely deployed in Bitcoin ecosystem |
| Bluetooth LE | ~1 MB practical | Proximity-based, no network required |
| Local Wi-Fi / peer-to-peer | Effectively unlimited | Proximity-based, highest throughput |
| Encrypted relay message | Relay size limits apply | Works at any distance, requires network connectivity |

### Recommendations

- Implementations SHOULD support at least one air-gapped transfer channel for security-sensitive users
- For small payloads (1-5 groups with few members), a single QR code or short BBQr animation is practical
- For larger payloads, implementations SHOULD offer a higher-bandwidth channel (Bluetooth, Wi-Fi, or relay-mediated transfer)
- Implementations MAY support multiple channels and select automatically based on payload size

## Publishing External Commits

After receiving and decrypting the pairing payload, the new device publishes its External Commits as standard `kind: 445` Group Events per [MIP-03](03.md).

### Construction

For each group in the pairing payload:

1. **Create MLS credential**: Generate a fresh MLS signing key. Create a `BasicCredential` with the identity field set to the user's raw 32-byte Nostr pubkey (per [MIP-00](00.md)).
2. **Build External Commit**: Using the `GroupInfo` from the pairing payload, construct an MLS External Commit containing:
   - One `ExternalInit` proposal (required by [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html))
   - One `PreSharedKey` proposal with the Resumption PSK (see [Resumption PSK Requirement](#resumption-psk-requirement))
   - An UpdatePath with the new device's LeafNode
   - The Nostr identity proof in `FramedContent.authenticated_data` (see [Nostr Identity Proof](#nostr-identity-proof))
3. **Serialize**: TLS-serialize the External Commit as an `MLSMessage`
4. **Encrypt outer layer**: Encrypt the serialized `MLSMessage` with NIP-44 using the `exporter_secret` from the pairing payload, following the standard `kind: 445` encryption process defined in [MIP-03](03.md)
5. **Create Nostr event**: Generate a fresh ephemeral keypair and publish as a `kind: 445` event with the `h` tag set to the `nostr_group_id` from the pairing payload

### Post-Join

After successfully joining a group via External Commit:

- The new device SHOULD perform a self-update Commit to rotate its signing key, following the self-update rules in [MIP-03](03.md)
- The new device begins receiving group messages from the new epoch onward
- The new device MUST NOT attempt to decrypt messages from epochs before it joined

## Device Name Extension (Optional)

Implementations MAY include a device name in the LeafNode to help users identify and manage their own devices. This extension is entirely optional and implementations MAY omit it.

### Extension Identifier

This extension uses the identifier `0xF2EF`. Implementations that support this extension MUST include `0xF2EF` in `LeafNode.capabilities.extensions` to satisfy the self-consistency requirement of [RFC 9420 Section 7.3](https://www.rfc-editor.org/rfc/rfc9420.html#section-7.3).

### Privacy-Preserving Design

Device names are sensitive metadata -- they reveal information about a user's hardware and usage patterns. To protect this information, the device name MUST be encrypted so that only the device owner can read it.

The device name is encrypted using NIP-44 with the user's own Nostr keypair:

```
conversation_key = NIP44.derive_conversation_key(nostr_privkey, nostr_pubkey)
encrypted_name = NIP44.encrypt(conversation_key, device_name_utf8)
```

Only devices holding the same Nostr private key can decrypt the device name. Other group members see the extension in the LeafNode but cannot read its content.

### TLS Structure

```tls
struct {
    opaque encrypted_device_name<V>;  // NIP-44 ciphertext of UTF-8 device name
} EncryptedDeviceName;
```

### LeafNode Integration

Per [RFC 9420 Section 13.4](https://www.rfc-editor.org/rfc/rfc9420.html#section-13.4), clients processing a LeafNode MUST ignore unknown extensions. This means:

- Clients that support `0xF2EF` can read and display device names for their own devices
- Clients that do not support `0xF2EF` silently ignore the extension with no interoperability impact
- No group-wide capability negotiation is required

### Usage

- The device name SHOULD be a short, human-readable label (e.g., "iPhone", "Desktop", "Laptop")
- The device name SHOULD be limited to 64 UTF-8 characters
- Clients MAY allow users to change the device name via a LeafNode update (self-update Commit)
- Clients that support this extension SHOULD display device names when the user manages their own devices (e.g., in a device management UI)
- Clients SHOULD NOT display device names for other users' devices (the extension cannot be decrypted without the user's Nostr private key)

## Client Recommendations

The following recommendations help ensure a consistent user experience across implementations.

### User Identity Coalescing

Clients SHOULD coalesce multiple leaf nodes with the same credential identity (Nostr pubkey) into a single logical user in the UI. For example, if Alice has two devices in a group, the member list should show "Alice" once (possibly with an indicator of 2 devices), not "Alice" twice.

### Own-Message Handling

When a user sends a message from one device, their other devices in the same group will receive it as a standard group message (since each device is an independent MLS leaf node). Clients SHOULD:

- Recognize messages from leaf nodes sharing the same Nostr pubkey as the local user
- Display such messages as sent messages rather than received messages
- Avoid duplicate notifications for messages sent from the user's other devices

### Device Management

Clients SHOULD provide users with a way to view which of their own devices are in each group. This can be done by inspecting the ratchet tree and filtering leaf nodes by credential identity. If the [Device Name Extension](#device-name-extension-optional) is supported, clients SHOULD display the decrypted device name alongside each device entry.

### Device Removal

Device removal is an application-level concern. When a user wants to remove a device from a group (e.g., a lost or compromised device), the user's remaining device creates a Remove proposal for the target leaf node and commits it (if the user is an admin) or submits it for admin approval. Clients SHOULD make it easy to remove a specific device from all groups at once.

### Forward Secrecy Disclosure

Clients SHOULD inform users that a newly added device cannot see messages from before it joined. This is a fundamental property of MLS forward secrecy and cannot be circumvented at the protocol level.

## Security Considerations

### Authentication Chain

External Commits for multi-device joins are validated through three independent mechanisms:

1. **`exporter_secret` knowledge** (outer NIP-44 encryption): The new device must know the current epoch's `exporter_secret` to produce a `kind: 445` event that existing members can decrypt. This secret can only be obtained from an existing group member.
2. **Resumption PSK** (MLS key schedule): The `confirmation_tag` will fail verification if the PSK value is incorrect. The `resumption_psk` can only be obtained from an existing group member who participated in the referenced epoch.
3. **Nostr identity proof** (`authenticated_data`): The Schnorr signature proves possession of the Nostr private key matching the credential identity. This cannot be forged without the Nostr private key.

An attacker must compromise all three to produce a valid External Commit.

### GroupInfo Confidentiality

GroupInfo objects contain group extensions (including `admin_pubkeys`, relay URLs, and the `nostr_group_id`) and the full ratchet tree (including all members' credentials and public keys). Exposure of GroupInfo to unauthorized parties reveals group membership and metadata.

The pairing payload MUST be encrypted before transfer regardless of the channel used. The encryption scheme (X25519 + ChaCha20-Poly1305) provides confidentiality and authenticity for the payload in transit.

### Cross-Device Correlation

Multiple leaf nodes with the same credential identity reveal to all group members that those nodes belong to the same user. The number of devices a user has in a group is observable. This is inherent to the multi-device model and cannot be avoided without fundamentally changing MLS's credential system.

See threat_model.md [T.13.7](threat_model.md) for analysis of cross-device correlation risks.

### Device Compromise Isolation

Each device maintains independent MLS state with its own signing key and encryption key. Compromise of one device does not compromise the key material of other devices. However, a compromised device has access to all group messages from its join epoch onward.

When a device is compromised:

- The user SHOULD remove the compromised device from all groups immediately
- Remaining devices SHOULD perform self-update Commits to rotate their key material
- Other group members are notified of the removal through the normal MLS Commit flow

See threat_model.md [T.13.6](threat_model.md) for analysis of device synchronization attacks.

### Epoch Race Conditions

GroupInfo and `exporter_secret` are epoch-specific. If any group member sends a Commit (including a self-update) between when the existing device extracts the pairing data and when the new device publishes its External Commit, the epoch will have advanced and the External Commit will fail.

Mitigations:

- The new device SHOULD publish External Commits as quickly as possible after receiving the pairing payload
- For multiple groups, the new device SHOULD publish External Commits in rapid succession
- Failed attempts SHOULD be retried with fresh GroupInfo from the existing device

See threat_model.md [T.13.8](threat_model.md) for analysis of device removal race conditions.

### Replay Protection

External Commits are bound to a specific group and epoch through the GroupContext included in `FramedContentTBS` ([RFC 9420 Section 6](https://www.rfc-editor.org/rfc/rfc9420.html#section-6)). The Nostr identity proof further binds the signature to the specific LeafNode and GroupContext. Replaying an External Commit for a different epoch or group will fail MLS validation.

### Group Size Impact

Each additional device adds a leaf node to the ratchet tree, increasing the group's effective size. This affects:

- **Welcome message size**: Larger ratchet trees produce larger Welcome messages, which may exceed relay size limits for groups approaching ~150 members
- **Commit processing**: More leaf nodes means more path computations during Commits

Implementations SHOULD consider the device-to-member ratio when evaluating group size limits.

### Admin Privilege Inheritance

Admin status in Marmot is based on the Nostr pubkey in `admin_pubkeys` ([MIP-01](01.md)), not on individual leaf nodes. All devices belonging to an admin automatically have admin privileges. This is by design -- admin authorization is identity-based, not device-based.
