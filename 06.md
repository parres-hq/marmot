# MIP-06

## Multi-Device Support

`draft` `optional`

This document defines how users can operate Marmot on multiple devices simultaneously. Each device is an independent MLS leaf node that joins existing groups via External Commits, authorized through an out-of-band device pairing flow. This specification covers the authorization model, pairing protocol, payload format, and client recommendations for multi-device scenarios.

## Overview

Marmot's identity model naturally supports multiple devices. Each device generates its own MLS signing key and encryption key, but all devices belonging to the same user share the same Nostr public key in their MLS `BasicCredential` identity field (see [MIP-00](00.md)). This means a user with two devices in a group will occupy two separate leaf nodes in the ratchet tree, but both leaf nodes carry the same credential identity.

The multi-device model has these properties:

- **Independent state**: Each device maintains its own MLS group state, key material, and message history. There is no shared MLS state between devices.
- **Same logical identity**: All devices share the same Nostr pubkey, allowing clients to recognize multiple leaf nodes as belonging to one user.
- **Independent decryption**: Each device independently receives and decrypts group messages. A message sent from one device will appear on the user's other devices as a group message.
- **Forward secrecy boundary**: A new device cannot decrypt messages from epochs before it joined. This is a fundamental MLS property and is by design.

History synchronization between devices is out of scope for this MIP and is deferred to a future specification.

## Multi-Device Signaling (CRITICAL)

To prevent state divergence between clients that do and do not implement this MIP, multi-device External Commit behavior MUST be explicitly signaled at the MLS group level.

### Extension Identifier

This extension uses identifier `0xF2F0`.

```tls
struct {
    uint16 version;  // current: 1
} MarmotMultiDevice;
```

Version rules:

- Version `0` is reserved and MUST be rejected.
- Version `1` is the current format.
- Higher versions MUST be rejected unless explicitly supported.

### Signaling Rules

A group that enables MIP-06 External Commit behavior MUST satisfy all of the following:

1. Include the `0xF2F0` `marmot_multi_device` extension in `GroupContext.extensions`.
2. Include `0xF2F0` in the group's `required_capabilities` extension list.
3. Ensure each member's `LeafNode.capabilities.extensions` includes `0xF2F0` (standard MLS compatibility rule).

### Compatibility Behavior

- If `0xF2F0` is **absent**, clients MUST treat External Commits from `new_member_commit` senders as unauthorized and reject them.
- If `0xF2F0` is **present**, clients MUST apply the External Commit authorization rules in this MIP.

This design lets groups decide at creation time (or through an explicit GroupContextExtensions update) whether MIP-06 behavior is enabled.

### Enabling MIP-06 in Existing Groups

Existing groups can enable MIP-06 later, but the rollout MUST be staged carefully:

1. Each current member that supports MIP-06 SHOULD update its current LeafNode capabilities to include `0xF2F0`, typically via a regular self-update Commit.
2. Clients that support MIP-06 SHOULD also re-publish future KeyPackages advertising `0xF2F0` so future group additions see consistent capability signaling.
3. Admins MUST NOT add `marmot_multi_device` to `GroupContext.extensions` or add `0xF2F0` to `required_capabilities` until every current leaf in the ratchet tree advertises support for `0xF2F0`.
4. Once all current leaves advertise support, an admin MAY commit a `GroupContextExtensions` update that enables `marmot_multi_device` and requires `0xF2F0` at the group level.
5. If any current member cannot update its LeafNode capabilities, the group MUST NOT enable MIP-06 until that member is removed or migrated.

## External Commit Authorization

Devices join existing groups via MLS External Commits ([RFC 9420 Section 12.4.3.2](https://www.rfc-editor.org/rfc/rfc9420.html#section-12.4.3.2)). An External Commit allows a new party to add themselves to a group using a `GroupInfo` object, without requiring an existing member to come online and issue an Add proposal.

### Authorization Carve-Out

[MIP-03](03.md) requires that Commits other than self-update Commits and SelfRemove-only Commits be sent by a member listed in `admin_pubkeys`. External Commits from new devices use a carve-out only when MIP-06 signaling is enabled (see [Multi-Device Signaling](#multi-device-signaling-critical)).

**An External Commit MUST be accepted when ALL of the following conditions are met:**

1. `marmot_multi_device` (`0xF2F0`) is present and valid in `GroupContext.extensions`
2. The credential identity (Nostr pubkey) in the joining LeafNode matches the credential identity of at least one existing group member
3. The External Commit includes exactly one valid Resumption PSK proposal (see [Resumption PSK Requirement](#resumption-psk-requirement))
4. The External Commit includes a valid Nostr identity proof in `FramedContent.authenticated_data` (see [Nostr Identity Proof](#nostr-identity-proof))
5. The External Commit contains no `Remove` proposals. MIP-06 permits only join-style External Commits, not resync-style External Commits that replace an existing leaf.
6. The External Commit satisfies all standard MLS validation rules ([RFC 9420 Section 12.4.2](https://www.rfc-editor.org/rfc/rfc9420.html#section-12.4.2))

**An External Commit MUST be rejected when:**

- The `marmot_multi_device` signaling extension is absent or invalid
- The credential identity does not match any existing member's credential identity
- The Resumption PSK proposal is missing or invalid
- The Nostr identity proof is missing or fails verification
- The External Commit includes any `Remove` proposal
- Any standard MLS validation check fails

This carve-out ensures that only the holder of a Nostr private key that is already represented in the group can add a new device, and only in groups that explicitly enabled this behavior.

### Validation Steps

When processing an External Commit, existing members MUST perform these checks in order:

1. Decrypt the outer group-event encryption layer using the current epoch's `group_event_key` (standard `kind: 445` processing per [MIP-03](03.md)).
2. Verify the MLS `PublicMessage` structure and signature per [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html).
3. Verify `GroupContext.extensions` contains a valid `marmot_multi_device` (`0xF2F0`) extension.
4. Validate the joining LeafNode per [RFC 9420 Section 7.3](https://www.rfc-editor.org/rfc/rfc9420.html#section-7.3) before using any fields from it.
5. Verify the credential identity in the joining LeafNode matches an existing member's credential identity.
6. Verify `authenticated_data` contains a valid Nostr identity proof (see [Nostr Identity Proof](#nostr-identity-proof)).
7. Verify exactly one `PreSharedKey` proposal is present and that:
   - `psktype == resumption`
   - `usage == application`
   - `psk_group_id == FramedContent.group_id`
   - `psk_epoch == FramedContent.epoch` (the current group epoch for this Commit)
   - `psk_nonce` length equals `KDF.Nh`
8. Verify the External Commit contains no `Remove` proposals.
9. Verify `confirmation_tag` during normal MLS Commit processing (this implicitly validates PSK value correctness).

If any check fails, the External Commit MUST be rejected.

## Nostr Identity Proof

The Nostr identity proof binds an External Commit to the Nostr private key of the joining user. It is placed in the `FramedContent.authenticated_data` field, which is an application-defined opaque byte string that is covered by the MLS signature ([RFC 9420 Section 6](https://www.rfc-editor.org/rfc/rfc9420.html#section-6)).

Unless explicitly stated otherwise, all quoted labels and domain-separation strings in this MIP are the ASCII byte sequences of the characters shown.

### Why `authenticated_data`

MLS External Commits are self-signed -- the joining device signs with its own MLS signing key, which is distinct from the Nostr identity key. Without an additional proof, there is no cryptographic link between the External Commit and the Nostr identity claimed in the credential. The `authenticated_data` field solves this:

- It is explicitly application-defined: "It is up to the application to decide what authenticated_data to provide" ([RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html))
- It is covered by the MLS signature, binding it cryptographically to the External Commit
- It requires no extension negotiation or group-wide capability advertisement
- It does not affect MLS processing for non-multi-device scenarios

For all Commit messages that are not MIP-06 External Commits, clients MUST set `FramedContent.authenticated_data` to the empty byte string unless another Marmot specification explicitly defines a non-empty value.

### Why a Canonical Nostr Event

MIP-06 uses a canonical unsigned Nostr event as the object being signed instead of a raw signed string.

This has two practical benefits:

- **Signer compatibility**: Many Nostr signers and remote-signing APIs expose standard Nostr event signing, but do not expose raw Schnorr-sign-an-arbitrary-challenge functionality.
- **Deterministic encoding**: A canonical Nostr event removes ambiguity about exactly which bytes are being signed. Fixed fields (`kind`, `created_at`, tag set, and hex-encoded challenge content) ensure all implementations derive the same signing preimage.

The dedicated proof-event `kind: 450` plus the fixed `"marmot-external-commit-auth-v1"` marker provide domain separation. This proof event MUST NOT be published to relays; it exists only as a local signing template.

### Proof Construction

The joining device constructs the Nostr identity proof as follows:

1. Serialize the LeafNode from the External Commit's UpdatePath using TLS serialization.
2. Serialize the TLS-serialized `GroupContext` for the epoch identified by this External Commit. On the joining device, this is the `GroupContext` contained in the `GroupInfo` used to construct the Commit.
3. Compute the challenge: `challenge = SHA-256(ASCII("marmot-external-commit-v1") || serialized_LeafNode || serialized_GroupContext)`.
4. Construct the following canonical unsigned Nostr proof event:

   ```json
   {
     "kind": 450,
     "created_at": 0,
     "pubkey": "<joining user's nostr pubkey>",
     "tags": [["m", "marmot-external-commit-auth-v1"]],
     "content": "<hex-encoded challenge>"
   }
   ```

   The `content` field uses the lowercase hex encoding of the 32-byte challenge rather than base64. This keeps the proof event content as a simple deterministic ASCII string and matches the verification rule below.

   This event MUST NOT be published to relays. It exists only as a signing template.
5. Sign that canonical proof event with the user's Nostr signing capability using standard Nostr event signing.

The `authenticated_data` field MUST contain the following TLS-serialized structure:

```tls
struct {
    uint16 version;                  // current: 1
    opaque nostr_event_sig[64];      // Nostr signature over canonical proof event id
} NostrIdentityProof;
```

### Proof Verification

Existing members verify the proof by:

1. Extract `NostrIdentityProof` from `FramedContent.authenticated_data`.
2. Verify `version == 1`.
3. Serialize the LeafNode from the External Commit's UpdatePath.
4. Serialize the TLS-serialized `GroupContext` for `FramedContent.epoch`.
5. Compute `challenge = SHA-256(ASCII("marmot-external-commit-v1") || serialized_LeafNode || serialized_GroupContext)`.
6. Reconstruct the canonical unsigned Nostr proof event with:
   - `kind = 450`
   - `created_at = 0`
   - `pubkey` = the Nostr pubkey from the LeafNode credential identity
   - `tags = [["m", "marmot-external-commit-auth-v1"]]`
   - `content = hex(challenge)` using lowercase hex without a prefix
7. Verify `nostr_event_sig` as a standard Nostr event signature over the reconstructed proof event id.

### Security Properties

- **Identity binding**: Proves the Nostr private key holder authorized this specific LeafNode to join this specific group at this specific epoch.
- **Replay prevention**: The GroupContext includes epoch and tree hash, preventing replay across epochs or groups.
- **Domain separation**: The `"marmot-external-commit-v1"` challenge prefix plus the dedicated proof-event kind/tag prevent cross-protocol signature reuse.
- **Signer compatibility**: Uses standard Nostr event signing APIs instead of requiring raw Schnorr-sign-challenge support.
- **Non-interference**: For Commit messages other than MIP-06 External Commits, `authenticated_data` stays empty unless another Marmot specification explicitly defines a non-empty value; existing MLS processing is otherwise unaffected.

## Resumption PSK Requirement

External Commits for multi-device joins MUST include exactly one `PreSharedKey` proposal with a Resumption PSK.

### PSK Configuration

The `PreSharedKey` proposal MUST use the following configuration:

- **`psktype`**: `resumption` (value `2`)
- **`usage`**: `application` (value `1`)
- **`psk_group_id`**: MUST equal the MLS group ID in `FramedContent.group_id`
- **`psk_epoch`**: MUST equal `FramedContent.epoch` (the current epoch being committed from)
- **`psk_nonce`**: Fresh cryptographically random value of length `KDF.Nh` for the target ciphersuite. The new device generates a new `psk_nonce` when constructing each External Commit; it is NOT carried in the pairing payload.

### How It Works

The `resumption_psk` is derived from the MLS key schedule ([RFC 9420 Section 8](https://www.rfc-editor.org/rfc/rfc9420.html#section-8)) and is available to current group members. The existing device provides the current-epoch `resumption_psk` value to the new device during pairing (see [Device Pairing Flow](#device-pairing-flow)).

When existing members process the External Commit:

1. They resolve the resumption PSK by `(psk_group_id, psk_epoch)`.
2. They derive `psk_secret` per [RFC 9420 Section 8.4](https://www.rfc-editor.org/rfc/rfc9420.html#section-8.4).
3. The `psk_secret` is incorporated into the new epoch key schedule.
4. `confirmation_tag` verification succeeds only if both sides used the same PSK material.

If the PSK is incorrect, `confirmation_tag` verification fails and the External Commit is rejected.

### Why Resumption PSK

Resumption PSKs are preferred over External PSKs because:

- Existing members already possess `resumption_psk` from their key schedule.
- PSK lookup is deterministic via group ID and epoch.
- It proves the new device received secret material from an existing member.

## Device Pairing Flow

Device pairing is an out-of-band exchange between an existing device (already a member of one or more groups) and a new device (not yet in any groups). The new device MUST already have access to the user's Nostr signing capability (for example via NIP-49 import, a signer, or direct local key storage) before initiating this flow, because it must create MLS credentials bound to that Nostr identity and sign the Nostr identity proof. Signer integrations used for MIP-06 MUST support signing the canonical proof event exactly as specified in this MIP.

### Phase 1: Bootstrap Key Exchange

1. New device generates a fresh X25519 keypair (`new_ephemeral_privkey`, `new_ephemeral_pubkey`).
2. New device presents `new_ephemeral_pubkey` (32 bytes) to the existing device.
3. New device MAY include channel hints for follow-up communication (for example, BLE advertisement info, local network candidate, or relay rendezvous token).

The bootstrap exchange MAY use any suitable channel: QR code, NFC tap, Bluetooth advertisement, or manual entry.

However, the bootstrap exchange MUST use an authenticated channel or an explicit user-verifiable key confirmation step. Unauthenticated broadcast discovery mechanisms (for example BLE advertisement alone) are insufficient on their own. If the transport does not inherently authenticate `new_ephemeral_pubkey`, the user MUST verify the displayed key or a fingerprint of it on both devices before any pairing payload is transferred.

### Phase 2: Existing Device Builds and Sends Pairing Payload

1. Existing device prompts the user to select groups the new device should join (all groups or subset).
2. Existing device generates a fresh X25519 keypair (`existing_ephemeral_privkey`, `existing_ephemeral_pubkey`) for this pairing session.
3. For each selected group, existing device extracts:
   - `GroupInfo` (with `external_pub` and `ratchet_tree` extensions)
   - current epoch `group_event_key` (the exact 32-byte outer encryption key defined in [MIP-03](03.md))
   - current epoch `resumption_psk`
4. Existing device assembles `PairingPayload` (see [Pairing Payload Specification](#pairing-payload-specification)).
5. Existing device encrypts payload using X25519 + HKDF-SHA256 + ChaCha20-Poly1305:
   - `shared_secret = X25519(existing_ephemeral_privkey, new_ephemeral_pubkey)`
   - If `shared_secret` is all-zero bytes, abort pairing
   - `prk = HKDF-SHA256-Extract(salt=ASCII("marmot-pairing-v1"), IKM=shared_secret)`
   - `key = HKDF-SHA256-Expand(prk, ASCII("marmot-pairing-key"), 32)`
   - Generate random 12-byte nonce
   - `aad = ASCII("marmot-pairing-v1") || new_ephemeral_pubkey || existing_ephemeral_pubkey`
   - `ciphertext = ChaCha20-Poly1305.encrypt(key, nonce, plaintext_payload, aad)`
   - Encrypted pairing message format: `existing_ephemeral_pubkey || nonce || ciphertext`
6. Existing device transfers encrypted pairing message to new device.
7. Existing device MUST securely delete `existing_ephemeral_privkey` and any pairing-only derived key material as soon as the transfer completes or aborts.

### Phase 3: New Device Decrypts, Validates, and Publishes

1. New device receives `existing_ephemeral_pubkey || nonce || ciphertext`.
2. New device computes:
   - `shared_secret = X25519(new_ephemeral_privkey, existing_ephemeral_pubkey)`
   - If `shared_secret` is all-zero bytes, abort pairing
   - Derive `key` with the same HKDF-SHA256 parameters
   - Recompute same AAD and decrypt payload
3. New device validates each group entry before constructing External Commit:
   - Parsed `GroupInfo.group_context.extensions` MUST contain a valid `marmot_multi_device` (`0xF2F0`) extension
   - Parsed group `required_capabilities` MUST require `0xF2F0`
   - Parsed `GroupInfo` MUST include `external_pub` and `ratchet_tree` extensions
   - Parsed `marmot_group_data` MUST be present and valid at `GroupInfo.group_context.extensions[type=0xF2EE].marmot_group_data`; use its `nostr_group_id` field for the `kind: 445` `h` tag
   - `len(group_event_key)` MUST equal `32`
   - `len(resumption_psk)` MUST equal `KDF.Nh` for the group ciphersuite
4. For each valid group entry, new device:
   a. Generates fresh MLS signing key and creates credential with its Nostr pubkey
   b. Constructs External Commit using provided `GroupInfo`
   c. Includes one Resumption PSK proposal (fresh `psk_nonce`)
   d. Includes Nostr identity proof in `authenticated_data`
   e. Wraps External Commit in `kind: 445` event (see [Publishing External Commits](#publishing-external-commits))
   f. Publishes event to group relays using the `nostr_group_id` extracted from `marmot_group_data`
5. After the pairing session completes or aborts, the new device securely deletes `new_ephemeral_privkey` and all retained pairing secrets.

### Retry Handling and Epoch Drift

`GroupInfo`, `group_event_key`, and `resumption_psk` are epoch-specific. If a group advances between payload generation and External Commit publication, that group join attempt fails.

#### Per-Group Retry Semantics

Each group attempt ends in one of:

- `success`: External Commit accepted.
- `stale_epoch`: Group advanced; refresh required.
- `fatal_error`: Data invalid (for example malformed GroupInfo, identity proof failure).

Retries are REQUIRED only for `stale_epoch` groups. Successful groups MUST NOT be retried.

#### Recommended Session Model

Implementations SHOULD support a pairing session model with incremental refresh:

1. Bootstrap with a low-bandwidth channel (for example QR) to exchange initial key material.
2. Upgrade to a bidirectional higher-bandwidth channel when available (for example Bluetooth LE, local Wi-Fi, or relay rendezvous).
3. New device reports per-group `stale_epoch` failures to existing device.
4. Existing device sends refreshed data only for failed groups in a fresh Phase 2-style encrypted message using the original `new_ephemeral_pubkey`, a newly generated `existing_ephemeral_privkey` / `existing_ephemeral_pubkey`, and updated current-epoch group data for those groups.
5. New device retries only those groups.

For MIP-06 v1, the original `new_ephemeral_pubkey` is the session recipient key for the entire pairing session. The new device MUST retain `new_ephemeral_privkey` until the session completes or aborts. The existing device MUST generate a fresh ephemeral X25519 keypair for every refresh message and MUST securely delete each refresh-specific ephemeral private key immediately after that transfer completes or aborts.

If no follow-up channel exists, implementations MUST restart pairing for failed groups.

#### Retry Requirements

For each retried group:

- Existing device MUST provide fresh current-epoch group data in a fresh Phase 2-style encrypted message.
- New device MUST create a new External Commit from scratch (new ExternalInit, fresh PSK nonce, new identity proof input bound to current GroupContext).
- Clients MUST NOT reuse stale `GroupInfo`, `group_event_key`, or `resumption_psk` from failed attempts.

## Pairing Payload Specification

The pairing payload is a TLS-serialized structure containing all data needed to issue External Commits.

### TLS Serialization Requirements

**CRITICAL**: Structures in this section are written using TLS presentation language notation ([RFC 8446 Section 3](https://www.rfc-editor.org/rfc/rfc8446.html#section-3)). In Marmot, all variable-length vectors use QUIC-style variable-length integer length prefixes ([RFC 9000 Section 16](https://www.rfc-editor.org/rfc/rfc9000.html#section-16)), consistent with [MIP-01](01.md) and the `tls_codec` crate. This is Marmot's wire-format convention; implementations MUST NOT use RFC 8446 fixed-width vector length prefixes for these fields.

### TLS Structures

```tls
struct {
    opaque group_event_key[32];       // exact key used by MIP-03 outer group-event encryption
    opaque resumption_psk<1..255>;    // MUST be length KDF.Nh
    opaque group_info<1..2^32-1>;     // TLS-serialized GroupInfo
} GroupPairingDataV1;

struct {
    uint16 version;                               // payload version (current: 1)
    GroupPairingDataV1 groups<1..2^32-1>;        // one entry per target group
} PairingPayload;
```

### Field Details

- **`version`**: Pairing payload format version. Current version is `1`. Version `0` is reserved and MUST be rejected.
- **`group_event_key`**: Exact 32-byte outer encryption key used for `kind: 445` group-event encryption in the current epoch, as defined by [MIP-03](03.md).
- **`resumption_psk`**: Current epoch resumption PSK. Length MUST be exactly `KDF.Nh` for the ciphersuite in `group_info`.
- **`group_info`**: TLS-serialized `GroupInfo` for current epoch. MUST include `external_pub` and `ratchet_tree` extensions and MUST carry valid MIP-06 signaling plus `marmot_group_data`. The new device extracts `group_id`, `epoch`, and `nostr_group_id` from `GroupInfo.group_context.extensions[type=0xF2EE].marmot_group_data.nostr_group_id` rather than receiving duplicate copies in the payload.

### Version Handling

- **Payload `version = 0`**: Reserved and MUST be rejected.
- **Payload `version = 1`**: Parse `groups` as a vector of `GroupPairingDataV1` entries.
- **Unknown payload version**: MUST be rejected.

### Consistency Checks

Before using a per-group entry, implementations MUST verify:

1. `GroupInfo.group_context.extensions` contains a valid `marmot_multi_device` (`0xF2F0`) extension
2. Parsed group `required_capabilities` requires `0xF2F0`
3. Parsed `GroupInfo` includes `external_pub` and `ratchet_tree`
4. Parsed `marmot_group_data` is present and valid at `GroupInfo.group_context.extensions[type=0xF2EE].marmot_group_data`, and its `nostr_group_id` field is used for the `h` tag
5. `group_event_key` length equals `32`
6. `resumption_psk` length equals `KDF.Nh`

Entries failing checks MUST be rejected before any External Commit is constructed.

### Confidentiality Requirements

The pairing payload contains highly sensitive group secrets and metadata. It MUST be encrypted in transit regardless of channel. Encryption and authentication requirements are defined in [Phase 2](#phase-2-existing-device-builds-and-sends-pairing-payload).

## Pairing Payload Size Estimates

The following table provides approximate payload sizes to help implementors choose transfer channels. Sizes are for raw TLS-serialized `PairingPayload` before encryption.

For ciphersuite `0x0001` (`KDF.Nh = 32`), per-group size is approximately `491 + 288 * N` bytes, where `N` is group member count.

For general ciphersuites, per-group size is approximately `459 + KDF.Nh + 288 * N` bytes.

### Size Reference Table

| Scenario | Groups | Avg members | Per-group size | Total payload | With compression (~30%) |
|---|---|---|---|---|---|
| Minimal | 1 | 5 | ~1.9 KB | **~1.9 KB** | ~1.4 KB |
| Light user | 5 | 10 | ~3.3 KB | **~16.5 KB** | ~11.5 KB |
| Typical user | 10 | 20 | ~6.1 KB | **~61 KB** | ~43 KB |
| Power user | 30 | 30 | ~8.9 KB | **~268 KB** | ~188 KB |
| Heavy user | 50 | 50 | ~14.5 KB | **~728 KB** | ~510 KB |

> **Note**: Table values assume ciphersuite `0x0001`. Larger `KDF.Nh` values increase per-group secret overhead.

### What Drives Size

- **Ratchet tree**: ~288 bytes per member (LeafNode ~219 bytes + ParentNode ~69 bytes); dominant factor.
- **GroupContext**: ~321 bytes per group (fixed fields + `marmot_group_data` extension).
- **GroupInfo overhead**: ~103 bytes per group (confirmation tag, signer, signature).
- **Pairing secrets**: approximately `33 + KDF.Nh` bytes per group plus length-prefix overhead.
- **Per-group framing**: versionless in payload v1; each entry is parsed directly as `GroupPairingDataV1` inside the outer `groups` vector.

## Transfer Channel Considerations

The pairing payload format is channel-agnostic. Implementations choose transfer mechanism based on user needs and payload size. This specification defines payload format and cryptographic requirements, not transport protocol.

### Channel Suitability

| Channel | Practical capacity | Characteristics |
|---|---|---|
| Single QR code | ~2 KB | Simple, suitable for 1 small group only |
| [BBQr](https://bbqr.org/) (animated QR) | Up to ~250 KB | Air-gapped, no network required |
| Bluetooth LE | ~1 MB practical | Proximity-based, bidirectional, retry-friendly |
| Local Wi-Fi / peer-to-peer | Effectively unlimited | Proximity-based, highest throughput |
| Encrypted relay message | Relay limits apply | Works at distance, needs network |

### Recommendations

- Implementations SHOULD support at least one air-gapped bootstrap channel.
- Implementations SHOULD support one bidirectional higher-bandwidth channel for incremental retries.
- The initial exchange of `new_ephemeral_pubkey` MUST use an authenticated channel or an explicit user-verification step; unauthenticated discovery alone is insufficient.
- For small payloads (1-5 groups with few members), single QR or short BBQr animation is practical.
- For larger payloads or retry-heavy sessions, implementations SHOULD offer Bluetooth, Wi-Fi, or relay-mediated transport.
- Implementations MAY auto-select channel by payload size and retry count.

## Publishing External Commits

After receiving and validating pairing payload entries, the new device publishes External Commits as standard `kind: 445` Group Events per [MIP-03](03.md).

### Construction

For each valid group entry:

1. **Create MLS credential**: Generate fresh MLS signing key. Create `BasicCredential` with identity = raw 32-byte Nostr pubkey (per [MIP-00](00.md)).
2. **Build External Commit**: Using payload `GroupInfo`, construct a join-style External Commit containing:
   - one `ExternalInit` proposal
   - exactly one `PreSharedKey` proposal with Resumption PSK
   - no `Remove` proposals
   - UpdatePath with new device LeafNode
   - Nostr identity proof in `FramedContent.authenticated_data`
3. **Serialize**: TLS-serialize External Commit as `MLSMessage`.
4. **Encrypt outer layer**: Encrypt serialized `MLSMessage` with the payload `group_event_key` using the standard group-event outer encryption defined in [MIP-03](03.md).
5. **Create Nostr event**: Generate fresh ephemeral keypair and publish `kind: 445` with `h` tag = `GroupInfo.group_context.extensions[type=0xF2EE].marmot_group_data.nostr_group_id`.

### Post-Join

After successful join via External Commit:

- New device begins receiving group messages from new epoch onward.
- New device MUST NOT attempt to decrypt messages from epochs before join.

## Device Name Extension (Optional)

Implementations MAY include a device name in LeafNode to help users identify and manage their own devices. This extension is optional.

### Extension Identifier

This extension uses identifier `0xF2EF`. Implementations supporting this extension MUST include `0xF2EF` in `LeafNode.capabilities.extensions` to satisfy [RFC 9420 Section 7.3](https://www.rfc-editor.org/rfc/rfc9420.html#section-7.3).

### Privacy-Preserving Design

Device names are sensitive metadata because they reveal hardware and usage patterns. Device name values MUST be encrypted so only the device owner can read them.

Device name encryption uses NIP-44 with the user's own Nostr keypair:

```
conversation_key = NIP44.derive_conversation_key(nostr_privkey, nostr_pubkey)
encrypted_name = NIP44.encrypt(conversation_key, device_name_utf8)
```

Only devices with the same Nostr private key can decrypt the value.

### TLS Structure

```tls
struct {
    opaque encrypted_device_name<1..2^16-1>;  // NIP-44 ciphertext of UTF-8 device name
} EncryptedDeviceName;
```

### LeafNode Integration

Per [RFC 9420 Section 13.4](https://www.rfc-editor.org/rfc/rfc9420.html#section-13.4), clients processing a LeafNode MUST ignore unknown extensions. This means:

- Clients supporting `0xF2EF` can read and display device names for their own devices.
- Clients not supporting `0xF2EF` ignore the extension without interoperability impact.
- No group-wide capability negotiation is required for this optional extension.

### Usage

- Device name SHOULD be a short label (for example, "iPhone", "Desktop", "Laptop").
- Device name SHOULD be limited to 64 UTF-8 characters.
- Clients MAY allow renaming via LeafNode update (self-update Commit).
- Clients supporting this extension SHOULD display names in local device management UI.
- Clients SHOULD NOT display undecryptable names for other users' devices.

## Client Recommendations

The following recommendations help ensure a consistent UX across implementations.

### User Identity Coalescing

Clients SHOULD coalesce multiple leaf nodes with the same credential identity (Nostr pubkey) into one logical user in the main chat UI. For example, if Alice has two devices, show "Alice" once (optionally with a "2 devices" indicator).

This is a presentation optimization only. Clients SHOULD still provide a device-management or audit view that shows each leaf separately, including per-device joins, removals, and which leaves currently inherit admin privileges.

### Own-Message Handling

When a user sends from one device, their other devices receive it as a standard group message. Clients SHOULD:

- Recognize leaf nodes sharing local user's Nostr pubkey.
- Render these as sent messages rather than received messages.
- Avoid duplicate notifications for cross-device self-messages.

### Device Management

Clients SHOULD provide a way to view which of the user's devices are in each group by inspecting ratchet tree leaves filtered by credential identity. If [Device Name Extension](#device-name-extension-optional) is supported, display decrypted device names.

### Device Addition Visibility

Clients SHOULD surface successful MIP-06 External Commits as explicit device-addition events rather than silently treating them as routine background synchronization. If the joining identity is listed in `admin_pubkeys`, clients SHOULD highlight that the new leaf inherits admin privileges.

Clients SHOULD also surface unusual repeated same-identity joins or rapid epoch churn so users and admins can detect compromised devices or abusive behavior.

### Device Removal

When removing a device (for example lost or compromised), remaining devices create Remove proposals for target leaves and commit them (if admin) or submit for admin approval. Clients SHOULD make it easy to remove a device from a specific group. Cross-group removal MAY be offered when the implementation can reliably identify the target device across groups, but this MIP does not currently define a mandatory stable cross-group device identifier or a special non-admin removal carve-out for same-identity sibling leaves.

Clients SHOULD also distinguish clearly between:

- **Leave this device**: remove only the current leaf, for example via SelfRemove
- **Leave all my devices**: remove every leaf in the group that carries the same Nostr credential identity

A SelfRemove only removes the sending leaf. If same-identity sibling leaves remain, clients SHOULD warn the user and MUST NOT present that action as having left the group entirely.

### Forward Secrecy Disclosure

Clients SHOULD inform users that newly added devices cannot read pre-join messages. This is an MLS forward secrecy property and cannot be bypassed at protocol level.

## Security Considerations

### Authentication Checks

External Commits for multi-device joins are validated through four checks spanning three trust domains:

1. **Group-level signaling**: MIP-06 behavior is active only when `marmot_multi_device` (`0xF2F0`) is present and valid.
2. **`group_event_key` knowledge** (outer group-event encryption): New device must know the current epoch's 32-byte outer encryption key to produce decryptable `kind: 445` content.
3. **Resumption PSK** (MLS key schedule): `confirmation_tag` fails if PSK input is wrong.
4. **Nostr identity proof** (`authenticated_data`): A standard Nostr event signature proves possession of the Nostr private key matching the credential identity.

Checks (2) and (3) are both rooted in current MLS secret material and are co-located in the pairing payload. If the pairing payload is compromised, those two checks collapse together. The remaining separation is still valuable: an attacker also needs the correct group signaling context and the Nostr signing capability for the claimed identity.

### GroupInfo and Pairing Payload Confidentiality

`GroupInfo` exposes group metadata and full ratchet tree public state. The pairing payload also carries secret values (`group_event_key`, `resumption_psk`). Exposure reveals sensitive group information and may enable active attacks.

The payload MUST be encrypted and authenticated in transit. Implementations MUST reject all-zero X25519 shared secrets and MUST use fresh ephemeral keypairs for each pairing message.

If a pairing session is canceled, abandoned, or suspected leaked, implementations SHOULD advance the epoch in each affected group (for example with a self-update Commit or any other valid Commit) before attempting pairing again. This invalidates previously transferred `group_event_key` / `resumption_psk` material for those groups.

If the compromised or newly added identity is an admin identity, every newly added leaf for that identity inherits admin privileges immediately. Clients SHOULD make this visible to users rather than treating it as an ordinary background state update.

### Cross-Device Correlation

Multiple leaves with same credential identity reveal that those leaves belong to one user. Device count per user within a group is observable. This is inherent to the model.

See threat_model.md [T.13.7](threat_model.md) for correlation analysis.

### Device Compromise Isolation

Each device maintains independent MLS state with its own signing and encryption keys. Compromise of one device does not directly compromise key material on other devices. However, compromised device can read messages from its join epoch onward.

When compromise is suspected:

- User SHOULD remove compromised device from all groups immediately.
- Remaining devices SHOULD perform self-update Commits.
- Group members observe removal through normal MLS Commit flow.

See threat_model.md [T.13.6](threat_model.md).

### Epoch Race Conditions

`GroupInfo`, `group_event_key`, and `resumption_psk` are epoch-specific. If any member commits between payload extraction and publication, stale attempts fail by design because the joiner is now targeting the wrong epoch state.

Mitigations:

- New device SHOULD publish quickly after receiving payload.
- Implementations SHOULD support per-group incremental retry with refreshed epoch data.
- Clients MUST never reuse stale per-group pairing entries after `stale_epoch` failure.

See threat_model.md [T.13.8](threat_model.md).

### Replay Protection

External Commits are bound to group and epoch through MLS `FramedContentTBS` context and confirmation-tag validation. Nostr identity proof further binds to specific LeafNode + GroupContext. Replay for different epoch or group fails validation.

### Group Size Impact

Each additional device adds a leaf to the ratchet tree, increasing effective group size. This affects:

- **Welcome size**: Larger trees increase Welcome payload size.
- **Commit cost**: More leaves increase path computations.

Implementations SHOULD consider device-to-user ratio when setting group size limits.

### Admin Privilege Inheritance

Admin status is identity-based (`admin_pubkeys` in [MIP-01](01.md)), not device-based. All devices for an admin identity inherit admin privileges.
