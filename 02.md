# MIP-02

## Welcome Events

`review` `mandatory`

This document defines Welcome Events (`kind: 444`) that enable secure group invitations in Marmot Protocol. Welcome Events provide everything new members need to join groups and begin the activation process for participation.

## Welcome Event Flow

### The Process

1. **Admin commits**: Group admin includes a new member via a `Commit` message
2. **Wait for confirmation**: Admin waits for relay acknowledgment of the Group Event
3. **Send Welcome**: Admin sends a private `Welcome` Event to the new member
4. **New member enters pending join**: New member processes the Welcome and begins catch-up
5. **New member activates**: After bounded catch-up and branch checks, the new member can start messaging

### Timing Requirements

Clients creating Welcome Events MUST:
1. **Wait for confirmation**: Don't send the Welcome until relays confirm receipt of the Commit
2. **Process before welcoming**: Ensure the group state change is committed before inviting

This sequencing prevents race conditions where a new member receives a Welcome for a group state that hasn't been finalized yet.

> #### CRITICAL: State Fork Prevention
>
> **This timing requirement applies to ALL member additions after initial group creation.** When adding members to an existing group, the Commit message MUST be accepted by relays BEFORE sending the Welcome message.
>
> **Why this matters**: The Welcome message contains the group state at a specific epoch. If the Welcome is delivered before the Commit reaches existing members, a **state fork** occurs:
>
> - The new member activates at epoch N+1 (from the Welcome)
> - Existing members remain at epoch N (haven't received the Commit yet)
> - Messages sent by the new member cannot be decrypted by existing members
> - Messages sent by existing members cannot be decrypted by the new member
> - The group state diverges, requiring manual recovery
>
> **This is not a theoretical concern**—distributed relay networks can deliver messages out of order. The only reliable prevention is waiting for relay confirmation of the Commit before sending the Welcome.
>
> **Note**: Initial group creation (single-member group with no prior epochs) does not require this wait because there are no existing members who could have a conflicting state.

## Privacy and Security

Welcome delivery uses [NIP-59](https://github.com/nostr-protocol/nips/blob/master/59.md) gift-wrapping for privacy and unlinkability. In Marmot, the outer `kind: 1059` gift-wrap is only a transport wrapper. The actual application-defined Welcome payload is carried in the inner unsigned rumor event.

The outer gift-wrap SHOULD reveal only the minimum metadata required for routing, typically the recipient `p` tag. Clients SHOULD NOT place parent Commit references or other branch-linking metadata on the outer `kind: 1059` event.

## Welcome Rumor Structure

```json
{
  "id": "def456...",
  "kind": 444,
  "created_at": 1693876600,
  "pubkey": "02a1633cafe37eeebe2b39b4ec5f3d74c35e61fa7e7e6b7b8c5f7c4f3b2a1b2c3d",
  "content": "MDk4NzY1NDMyMWZlZGNiYS4uLg==",
  "tags": [
    ["e", "keypackage_event_id_123..."],
    ["commit", "parent_group_event_id_456..."],
    ["epoch", "12"],
    ["relays", "wss://relay1.com", "wss://relay2.com"],
    ["encoding", "base64"]
  ]
}
```

**Important**: This event is NOT signed (`"sig"` field omitted) to prevent accidental public publishing if it leaks.

### Field Details

**Required fields:**
- **`content`**: Serialized `MLSMessage` containing the MLS `Welcome` object, base64-encoded.
- **`encoding`**: Specifies the encoding format of the `content` field. MUST be `["encoding", "base64"]`. Implementations MUST reject events with missing or unrecognized encoding tags. Hex encoding was used by early implementations but is no longer supported and MUST be rejected.
- **`e` tag**: ID of the KeyPackage Event used to add this user
- **`commit` tag**: ID of the parent `kind: 445` Commit event that produced the Welcome branch. This tag exists inside the private rumor so the recipient can reason about the intended branch without exposing the linkage publicly on the outer gift-wrap.
- **`epoch` tag**: Decimal string encoding of the post-Commit epoch carried by this Welcome. This tag is RECOMMENDED and improves diagnostics and branch conflict handling.
- **`relays` tag**: List of relays where the new member should look for Group Events

**Security note**: The unsigned nature prevents the event from being accidentally published to public relays, as most relays reject unsigned events.

### Parent Commit Binding

Welcome rumors MUST identify the exact parent `kind: 445` Commit event from which the Welcome was generated using the `commit` tag. This binding is a Marmot coordination hint, not a replacement for MLS validation. Recipients MUST still cryptographically validate the MLS Welcome and resulting group state.

Binding the parent Commit privately in the rumor provides three important benefits:

- it lets the joiner fetch and verify the intended branch,
- it allows deterministic handling of same-epoch competing Commits,
- and it avoids exposing direct branch-link metadata on public relay-visible event surfaces.

## Welcome Event Content

### MLS Welcome Object

The `content` field contains a base64-encoded MLS `Welcome` object. The encoding format (base64 or hex) is specified by the `encoding` tag. The Welcome object includes:

- **Group secrets**: Cryptographic keys needed to decrypt group messages
- **Group state**: Current member list and group configuration
- **Ratchet tree**: Key tree structure for the group
- **Extensions**: Group metadata including Marmot Group Data Extension

### Processing Requirements

When receiving a Welcome Event, clients MUST:

1. **Verify KeyPackage match**: Ensure the referenced KeyPackage belongs to this user
2. **Verify private branch binding**: Parse the `commit` tag and verify it references the parent `kind: 445` Commit event that the inviter intended the recipient to follow. If present, clients SHOULD also parse the `epoch` tag.
3. **Process MLS Welcome**: Use MLS library to process the Welcome and create local candidate group state
4. **Validate group state**: Verify all group extensions and configurations, including the mandatory Marmot Group Data Extension (`0xF2EE`)
5. **Enter PendingJoin**: Mark the local group state as `PendingJoin` rather than immediately treating the group as fully active
6. **Store group information**: Save group keys, member list, relay information, and the bound parent Commit reference
7. **Rotate KeyPackage**: Remove the consumed KeyPackage from relays, optionally post a new fresh Keypackage
8. **Delete init_key**: Securely delete the private init_key material from local storage (see [MIP-00](00.md) Private Key Material Management)
9. **Perform bounded catch-up**: Attempt to fetch and process outstanding Commits for the group before activation and before self-update (see below)

### Join Activation States

To reduce activation of stale or losing branches, Marmot clients SHOULD implement the following local states:

- **`PendingJoin`**: A Welcome was processed successfully, but the client has not yet completed branch checks and bounded catch-up.
- **`Active`**: The client considers the join sufficiently converged for normal messaging.
- **`StateUncertain`**: The client has evidence of competing branches, stale local state, or unresolved drift and must pause outbound activity.
- **`Quarantined`**: The client determined that the joined branch is inconsistent, invalid, or losing and MUST NOT use it for messaging.

These are local client states used to improve convergence and recovery. They do not alter MLS cryptographic validation rules.

### Activation Requirements

After processing a Welcome, clients MUST enter `PendingJoin` and MUST NOT immediately begin normal messaging.

While in `PendingJoin`, clients MUST:

1. attempt bounded catch-up from the configured relay set,
2. attempt to fetch and process the parent Commit identified by the private `commit` tag,
3. avoid sending application messages,
4. avoid sending structural proposals or Commits,
5. defer self-update until the bounded catch-up attempt completes.

Clients MAY transition from `PendingJoin` to `Active` only after all of the following are true:

1. the MLS Welcome and resulting group state validated successfully,
2. the client completed a bounded catch-up attempt across all currently reachable configured relays,
3. the client located or otherwise reconciled the parent Commit branch referenced by the Welcome rumor,
4. no known same-epoch winning Commit invalidates the Welcome branch,
5. the client has not entered `StateUncertain` or `Quarantined`.

If these conditions are not met, the client MUST remain `PendingJoin`, enter `StateUncertain`, or enter `Quarantined` depending on the observed failure mode.

### Bounded Catch-Up

For Welcome activation and post-join self-update, a bounded catch-up attempt means:

1. query all relay URLs in the authenticated group state that are currently reachable,
2. fetch recent unseen `kind: 445` events for the group,
3. process all Commits and relevant Proposals that can be validated and applied,
4. stop when no additional processable events remain or when the implementation's configured timeout budget expires.

The catch-up procedure is bounded to avoid indefinite waiting on unavailable or adversarial relays. Failure to achieve certainty does not authorize unsafe activation; it requires the client to remain conservative.

### Post-Join Self-Update Requirement

After successfully processing a Welcome message, clients SHOULD perform a self-update (MLS Update proposal for their own LeafNode) as soon as possible. However, that self-update SHOULD be sent only after the bounded catch-up attempt described above completes so the self-update is based on the freshest available group state. Sending a self-update from stale state increases the risk of local state divergence (effectively "forking yourself" out of the group).

#### Why Self-Update Matters

When a member joins via a Welcome message, their LeafNode contains the key material from the KeyPackage that was used to add them. This means:

1. **The init_key was potentially exposed**: The KeyPackage was published to relays and may have been observed or captured by adversaries
2. **Forward secrecy is limited**: Until the member updates their LeafNode, any compromise of the init_key private material could allow decryption of group secrets

By performing an immediate self-update:
- Fresh key material is generated that was never published or observable
- The group epoch advances, providing forward secrecy for subsequent messages
- The risk window from KeyPackage exposure is minimized

#### Self-Update Timing

- **RECOMMENDED order**: After processing Welcome, first attempt to process outstanding Commits, then perform a self-update as soon as possible
- **RECOMMENDED target**: Complete the self-update before sending application messages whenever feasible
- **MUST**: Perform self-update within 24 hours of joining the group, even if catch-up is partial due to relay availability

If a client cannot process all outstanding Commits immediately (for example, relay unavailability), it SHOULD continue catch-up attempts and avoid sending application messages until it confirms it is on the current group epoch. If branch ambiguity, a missing parent Commit, or other drift evidence remains unresolved, the client SHOULD remain `PendingJoin` or enter `StateUncertain` instead of self-updating from uncertain state.

#### Implementation Note

Self-update Commits are explicitly allowed from any group member, regardless of admin status (see [MIP-03](03.md)). This ensures all members can maintain their own key hygiene without requiring admin privileges.

> #### Large Groups
>
> For groups above ~150 participants, welcome messages will become larger than is permitted by many Nostr relays. There is currently work underway on the MLS protocol to support "light" client `Welcome` objects that don't require the full Ratchet Tree state to be sent to the new member. This section will be updated with recommendations for how to handle large groups.

## Error Handling

### Welcome Processing Failures

If Welcome processing fails, clients SHOULD:

1. **Retain KeyPackage**: Do NOT delete the KeyPackage from relays
2. **Display clear errors**: Show user-friendly error messages
3. **Log technical details**: Capture technical information for debugging

### Activation and Branch Failures

If a Welcome validates cryptographically but the client cannot safely activate it, clients SHOULD:

1. **Remain conservative**: Keep the group in `PendingJoin` or `StateUncertain`
2. **Retry bounded catch-up**: Re-query configured relays for the parent Commit and any competing Commits
3. **Quarantine losing or inconsistent state**: If the Welcome branch is determined to be losing or structurally inconsistent, move the local state to `Quarantined`
4. **Fail closed**: Do NOT send application messages from unresolved state
5. **Request recovery**: Surface that re-invitation or manual recovery may be required if uncertainty persists

### Common Failure Scenarios

- **Signing key unavailable**: KeyPackage was created on a different device thus the secret key for the KeyPackage used to add the user to the group is not available.
- **Parent Commit missing**: The Welcome rumor references a parent `kind: 445` Commit that is not yet visible on reachable relays. The client should remain `PendingJoin` and continue bounded catch-up.
- **Losing Welcome branch**: A competing same-epoch Commit wins according to Marmot's conflict rules, invalidating the branch referenced by the Welcome. The client must quarantine that join state and require re-invitation.
- **Ratchet tree inconsistency**: MLS library validation rejects the Welcome branch due to tree invariant failures. This indicates inconsistent or poisoned state and must not be bypassed.

## Summary

Welcome Events are the secure onboarding mechanism for Marmot groups:

### Key Components

1. **MLS Welcome Object**: Contains all cryptographic material for group access
2. **Gift-Wrapping**: Provides privacy and unlinkability using NIP-59
3. **KeyPackage Reference**: Links Welcome to the consuming KeyPackage
4. **Private Parent Commit Binding**: Privately links the Welcome to its intended parent Commit branch
5. **Relay Information**: Tells new members where to find Group Events

### Implementation Requirements

**MUST implement**:
- NIP-59 gift-wrapping with unsigned events
- Proper timing (wait for Commit confirmation)
- Private parent Commit binding in the Welcome rumor
- `PendingJoin` behavior with bounded catch-up before activation
- KeyPackage lifecycle management (relay deletion)
- Private init_key secure deletion after Welcome processing
- Self-update within 24 hours of joining (RECOMMENDED: attempt Commit catch-up first, then self-update as soon as possible)
- Graceful error handling with clear user messages
