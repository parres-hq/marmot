# MIP-02

## Welcome Events

`review` `mandatory`

This document defines Welcome Events (`kind: 444`) that enable secure group invitations in Marmot Protocol. Welcome Events provide everything new members need to join groups and begin participation.

## Welcome Event Flow

### The Process

1. **Admin commits**: Group admin includes a new member via a `Commit` message
2. **Wait for confirmation**: Admin waits for relay acknowledgment of the Group Event
3. **Send Welcome**: Admin sends a private `Welcome` Event to the new member
4. **New member joins the group**: New member processes the Welcome for the epoch created by the Commit
5. **New member syncs before sending**: Before sending application messages or a self-update, the new member SHOULD make a bounded best-effort attempt to process any newer visible group state

### Timing Requirements

Clients creating Welcome Events MUST:
1. **Wait for confirmation**: Don't send the Welcome until relays confirm receipt of the Commit
2. **Process before welcoming**: Ensure the group state change is committed before inviting

This sequencing prevents race conditions where a new member receives a Welcome for a group state that hasn't been finalized yet.

> #### CRITICAL: State Fork Prevention
>
> **This timing requirement applies to ALL member additions after initial group creation.** When adding members to an existing group, the Commit message MUST be accepted by relays BEFORE sending the Welcome message.
>
> **Why this matters**: The Welcome message contains the group state at a specific epoch. If the Welcome is delivered before the Commit reaches existing members, a **state fork** occurs:
>
> - The new member activates at epoch N+1 (from the Welcome)
> - Existing members remain at epoch N (haven't received the Commit yet)
> - Messages sent by the new member cannot be decrypted by existing members
> - Messages sent by existing members cannot be decrypted by the new member
> - The group state diverges, requiring manual recovery
>
> **This is not a theoretical concern**—distributed relay networks can deliver messages out of order. The only reliable prevention is waiting for relay confirmation of the Commit before sending the Welcome.
>
> **Note**: Initial group creation (single-member group with no prior epochs) does not require this wait because there are no existing members who could have a conflicting state.

## Privacy and Security

Welcome delivery uses [NIP-59](https://github.com/nostr-protocol/nips/blob/master/59.md) gift-wrapping for privacy and unlinkability. In Marmot, the outer `kind: 1059` gift-wrap is only a transport wrapper. The actual application-defined Welcome payload is carried in the inner unsigned rumor event.

The outer gift-wrap SHOULD reveal only the minimum metadata required for routing, typically the recipient `p` tag. Clients SHOULD NOT place parent Commit references or other branch-linking metadata on the outer `kind: 1059` event.

## Welcome Rumor Structure

```json
{
  "id": "def456...",
  "kind": 444,
  "created_at": 1693876600,
  "pubkey": "02a1633cafe37eeebe2b39b4ec5f3d74c35e61fa7e7e6b7b8c5f7c4f3b2a1b2c3d",
  "content": "MDk4NzY1NDMyMWZlZGNiYS4uLg==",
  "tags": [
    ["e", "keypackage_event_id_123..."],
    ["relays", "wss://relay1.com", "wss://relay2.com"],
    ["encoding", "base64"]
  ]
}
```

**Important**: This event is NOT signed (`"sig"` field omitted) to prevent accidental public publishing if it leaks.

### Field Details

**Required fields:**
- **`content`**: Serialized `MLSMessage` containing the MLS `Welcome` object, base64-encoded.
- **`encoding`**: Specifies the encoding format of the `content` field. MUST be `["encoding", "base64"]`. Implementations MUST reject events with missing or unrecognized encoding tags. Hex encoding was used by early implementations but is no longer supported and MUST be rejected.
- **`e` tag**: ID of the KeyPackage Event used to add this user
- **`relays` tag**: List of relays where the new member should look for Group Events

**Optional fields:**
- **`ea` tag**: Hex-encoded MLS `epoch_authenticator` for the Welcome epoch. This tag is OPTIONAL for backwards compatibility, but conforming clients that support it SHOULD include and validate it because it provides a compact same-epoch branch confirmation signal.

**Security note**: The unsigned nature prevents the event from being accidentally published to public relays, as most relays reject unsigned events.

## Welcome Event Content

### MLS Welcome Object

The `content` field contains a base64-encoded MLS `Welcome` object. The encoding format (base64 or hex) is specified by the `encoding` tag. The Welcome object includes:

- **Group secrets**: Cryptographic keys needed to decrypt group messages
- **Group state**: Current member list and group configuration
- **Ratchet tree**: Key tree structure for the group
- **Extensions**: Group metadata including Marmot Group Data Extension

### Processing Requirements

When receiving a Welcome Event, clients MUST:

1. **Verify KeyPackage match**: Ensure the referenced KeyPackage belongs to this user
2. **Parse optional private hints**: If present, parse the `ea` tag as coordination metadata
3. **Process MLS Welcome**: Use MLS library to process the Welcome and initialize local group state for the Welcome epoch
4. **Validate MLS tree state**: Perform normal MLS Welcome validation, including validation of the ratchet tree against the `tree_hash` carried in `GroupInfo.group_context`
5. **Validate group state**: Verify all group extensions and configurations, including the mandatory Marmot Group Data Extension (`0xF2EE`)
6. **Compare encrypted epoch confirmation when available**: If the `ea` tag is present and the client can derive the local Welcome-epoch `epoch_authenticator`, compare the values before first outbound traffic
7. **Store group information**: Save group keys, member list, relay information, and any optional private hints
8. **Rotate KeyPackage**: Remove the consumed KeyPackage from relays, optionally post a new fresh Keypackage
9. **Delete init_key**: Securely delete the private init_key material from local storage (see [MIP-00](00.md) Private Key Material Management)

### Welcome-Epoch Consistency Checks

Marmot relies on two different consistency mechanisms during Welcome processing:

1. **MLS-native tree validation**: The ratchet tree carried by the Welcome MUST validate against the `tree_hash` in `GroupInfo`.
2. **Marmot epoch confirmation**: If present, the `ea` tag carries the inviter's MLS `epoch_authenticator` for the Welcome epoch. This gives the joiner a compact same-epoch branch confirmation signal after successful Welcome processing.

In mixed-client environments, implementations SHOULD include this `ea` tag. Omitting it removes one of the few low-overhead checks that can detect same-epoch divergence before a newly joined client starts sending traffic.

These checks serve different purposes:

- `tree_hash` validation detects structural inconsistency in the Welcome-derived group state,
- `epoch_authenticator` comparison detects whether inviter and joiner derived the same Welcome-epoch cryptographic state.

Matching `epoch_authenticator` values do not prove that no newer Commit exists elsewhere. They do provide strong evidence that the joiner and inviter agree on the joined epoch itself.

### Post-Join Send Discipline

After processing a Welcome successfully, the recipient is a member of the group in the Welcome epoch. Marmot does not define a separate protocol activation state for that join.

However, in a decentralized relay environment, newer Commits may already be visible on some relays by the time the new member comes online. Before sending application messages or a self-update, clients SHOULD make a bounded best-effort attempt to process newer visible group state.

A bounded best-effort sync means:

1. query all relay URLs in the authenticated group state that are currently reachable,
2. fetch recent unseen `kind: 445` events for the group,
3. process all Commits and relevant Proposals that can be validated and applied,
4. stop when no additional processable events remain or when the implementation's configured timeout budget expires.

This sync is bounded to avoid indefinite waiting on unavailable or adversarial relays.

If the client observes evidence of drift, same-epoch conflict, or other uncertainty during this sync, it SHOULD pause outbound traffic and follow the recovery guidance in [MIP-03](03.md).

If the `ea` tag is present and the derived local `epoch_authenticator` does not match, the client MUST treat the joined state as drifted or forked, MUST quarantine that state, and MUST NOT send application messages, self-updates, or structural Commits from it.

In mixed-client environments, clients SHOULD treat absence of the `ea` tag as reduced confidence in same-epoch branch confirmation and SHOULD continue operating conservatively until bounded catch-up completes.

### Post-Join Self-Update Requirement

After successfully processing a Welcome message, clients SHOULD perform a self-update (MLS Update proposal for their own LeafNode) as soon as possible. However, that self-update SHOULD be sent only after the bounded best-effort sync described above completes so the self-update is based on the freshest visible group state. Sending a self-update from stale state increases the risk of local state divergence (effectively "forking yourself" out of the group).

#### Why Self-Update Matters

When a member joins via a Welcome message, their LeafNode contains the key material from the KeyPackage that was used to add them. This means:

1. **The init_key was potentially exposed**: The KeyPackage was published to relays and may have been observed or captured by adversaries
2. **Forward secrecy is limited**: Until the member updates their LeafNode, any compromise of the init_key private material could allow decryption of group secrets

By performing an immediate self-update:
- Fresh key material is generated that was never published or observable
- The group epoch advances, providing forward secrecy for subsequent messages
- The risk window from KeyPackage exposure is minimized

#### Self-Update Timing

- **RECOMMENDED order**: After processing Welcome, first attempt to process newer visible Commits, then perform a self-update as soon as possible
- **RECOMMENDED target**: Complete the self-update before sending application messages whenever feasible
- **MUST**: Perform self-update within 24 hours of joining the group, even if catch-up is partial due to relay availability

If a client cannot process all newer visible Commits immediately, it SHOULD continue sync attempts and avoid sending application messages until it has done reasonable best-effort reconciliation with reachable relays. If branch ambiguity or other drift evidence remains unresolved, it SHOULD avoid self-updating from uncertain state.

#### Implementation Note

Self-update Commits are explicitly allowed from any group member, regardless of admin status (see [MIP-03](03.md)). This ensures all members can maintain their own key hygiene without requiring admin privileges.

> #### Large Groups
>
> For groups above ~150 participants, welcome messages will become larger than is permitted by many Nostr relays. There is currently work underway on the MLS protocol to support "light" client `Welcome` objects that don't require the full Ratchet Tree state to be sent to the new member. This section will be updated with recommendations for how to handle large groups.

## Error Handling

### Welcome Processing Failures

If Welcome processing fails, clients SHOULD:

1. **Retain KeyPackage**: Do NOT delete the KeyPackage from relays
2. **Display clear errors**: Show user-friendly error messages
3. **Log technical details**: Capture technical information for debugging

### Activation and Branch Failures

If a Welcome validates cryptographically but the client later observes uncertainty or drift related to the joined state, clients SHOULD:

1. **Remain conservative**: Pause outbound application messages and avoid structural Commits
2. **Retry bounded sync**: Re-query configured relays for newer Commits and competing branches
3. **Quarantine losing or inconsistent state**: If the joined branch is determined to be losing or structurally inconsistent, quarantine that local state
4. **Fail closed**: Do NOT send application messages from unresolved state
5. **Request recovery**: Surface that re-invitation or manual recovery may be required if uncertainty persists

If MLS Welcome processing fails tree validation or other structural validation tied to `GroupInfo.group_context.tree_hash`, clients MUST treat the Welcome as inconsistent group state rather than as a mere transport failure.

If the `ea` tag is present and does not match the locally derived Welcome-epoch `epoch_authenticator`, clients MUST:

1. **Fail closed**: Do NOT continue to use the joined state for messaging
2. **Quarantine the branch**: Mark the local state as drifted or forked
3. **Avoid outbound traffic**: Do NOT send application messages, self-updates, or structural Commits from that state
4. **Require recovery**: Re-invitation or explicit recovery is required before proceeding

### Common Failure Scenarios

- **Signing key unavailable**: KeyPackage was created on a different device thus the secret key for the KeyPackage used to add the user to the group is not available.
- **Newer Commit visible after join**: The client processes a Welcome successfully, then discovers a later visible Commit before sending. The client should process that Commit before sending application traffic or self-updating.
- **Losing Welcome-producing branch**: A competing same-epoch Commit wins according to Marmot's conflict rules, invalidating the joined branch. The client must quarantine that join state and require re-invitation.
- **Ratchet tree inconsistency**: MLS library validation rejects the Welcome branch due to tree invariant failures. This indicates inconsistent or poisoned state and must not be bypassed.
- **Epoch confirmation mismatch**: Welcome processing succeeds, but the encrypted `ea` tag differs from the locally derived `epoch_authenticator`. This indicates same-epoch branch divergence or inconsistency and requires quarantine.

## Summary

Welcome Events are the secure onboarding mechanism for Marmot groups:

### Key Components

1. **MLS Welcome Object**: Contains all cryptographic material for group access
2. **Gift-Wrapping**: Provides privacy and unlinkability using NIP-59
3. **KeyPackage Reference**: Links Welcome to the consuming KeyPackage
4. **Relay Information**: Tells new members where to find Group Events
5. **Optional Private Hints**: May carry encrypted coordination metadata such as epoch, or `epoch_authenticator` without exposing it publicly

### Implementation Requirements

**MUST implement**:
- NIP-59 gift-wrapping with unsigned events
- Proper timing (wait for Commit confirmation)
- KeyPackage lifecycle management (relay deletion)
- Private init_key secure deletion after Welcome processing
- Self-update within 24 hours of joining (RECOMMENDED: first attempt bounded best-effort sync, then self-update as soon as possible)
- Graceful error handling with clear user messages

**SHOULD implement**:
- Bounded best-effort sync after joining and before first outbound traffic
- Conservative pause-and-recover behavior when newer visible state or branch uncertainty is detected
- Optional `epoch_authenticator` confirmation for Welcome-epoch branch checking, especially in mixed-client environments
- Optional private parent Commit hints only as diagnostics, not as a requirement for correct join processing
